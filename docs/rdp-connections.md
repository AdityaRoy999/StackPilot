# Remote desktops inside StackPilot

Open **Settings → Remote Connections → Remote desktops**. Choose **Add desktop**, or **Import .rdp** to upload an existing connection file. Review the host, port, Windows account, and domain, enter the account password, then save. Choose **Open** to use the desktop inside StackPilot. The viewer supports mouse, keyboard, touchpad input, dynamic resizing, fullscreen, Ctrl + Alt + Delete, reconnect, and disconnect. The **Remote** page is for accessing StackPilot from your other devices.

Import accepts UTF-8 and BOM-marked UTF-16 `.rdp` files up to 64 KB, including hostname/IPv4/IPv6 and a custom port. A Windows-encrypted `password 51` is not portable and is never imported; enter the password separately. Import fills a review form without saving or connecting automatically. Files requiring RD Gateway, RemoteApp, RDS broker routing, or unsupported authentication are explicitly blocked. This release supports direct full-desktop RDP with NLA, TLS, or automatic negotiation. Keyboard layouts are configurable in Advanced. Clipboard, drives, printing, audio, and microphone redirection are disabled in this release.

On Windows, enable **Settings → System → Remote Desktop** and allow the selected account to connect. The host must run an edition capable of hosting Remote Desktop, such as Windows Pro or Windows Server; Windows Home cannot host RDP. StackPilot’s server/bridge must be able to reach the machine and its RDP port (normally 3389), for example through your private network or VPN. `localhost` refers to the bridge container, not your Windows PC. Keep the PC awake. See [Microsoft’s Remote Desktop setup](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remotepc/remote-desktop-allow-access).

Certificate validation is enabled by default. For a trusted isolated VM using a self-signed certificate, explicitly enable **Allow this host’s self-signed certificate**. NLA requires the account password. RDP desktop access is separate from SSH connections and native build-worker enrollment.

## Installation and operation

Both Compose configurations include `rdp-gateway` and the private `rdp-bridge` (`guacamole/guacd:1.6.0`). Run `docker compose up -d --build rdp-gateway rdp-bridge frontend` after updating. The Next.js proxy and production Caddy route `/api/v1/rdp/*` and `/ws/rdp` to the gateway. No guacd TCP port is published. The gateway uses the existing Postgres database, backend account authentication, and `TOKEN_ENCRYPTION_KEY`; preserve that key across upgrades. Migration `070_rdp_connections.sql` is idempotent and also applied by the gateway at startup so it can start before a backend image upgrade.

Set `RDP_ALLOWED_ORIGINS` to comma-separated exact browser origins (for example `https://stack.example.com`). It defaults to `CORS_ALLOWED_ORIGIN`. Use HTTPS/WSS in production. RDP API calls deliberately use the same-origin proxy even when the platform’s general API uses a separate backend URL. A custom phone gateway needs equivalent routes and an explicitly allowed origin; the managed phone tunnel is not an RDP transport in this release.

Saved passwords use the existing AES-256-GCM envelope and never appear in connection responses, import responses, audit events, or model context. Connections belong to the signed-in account. WebSockets require an allowed origin and a random, single-use, 40-second capability. Authentication is rechecked before connecting and every ten seconds. Editing/removing a connection closes its sessions immediately. Sessions are capped at two per account, 32 per gateway, and four hours each; pending capabilities are bounded and invalidated on restart. Session start/end and connection changes appear in Audit Logs. Reconnect requires a fresh capability.

Run exactly one asynchronous gateway worker per instance. Capabilities and active-session coordination are in memory; multiple gateway replicas require a shared capability/session broker before load balancing. The bridge is on a dedicated Docker network, separate from application runtimes. This is a remote-desktop service, so only trusted authenticated accounts should be able to configure destinations reachable from its network.

The browser client is vendored from the official Apache source release with SHA-256 verification and Apache LICENSE/NOTICE files. Reproduce it with `python scripts/vendor-guacamole.py`. See [Apache’s RDP settings](https://guacamole.apache.org/doc/1.6.0/gug/configuring-guacamole.html) and [protocol documentation](https://guacamole.apache.org/doc/1.6.0/gug/guacamole-protocol.html).
